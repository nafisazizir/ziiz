# Migration state

Mutable state for the shadcn (Vega) → ziiz component migration. The
procedure itself — ground rules, decisions in force, the five passes — is
the `migrate-component` skill (`.agents/skills/migrate-component/SKILL.md`).
This file holds only what changes as the migration progresses: open
questions and the per-component decision log.

## Open questions (resolve before the component that hits them)

- /materials Surface-tier copy is stale after card settled flat (2026-08-16):
  material-medium still says "Raised surfaces: cards at rest or on hover" and
  material-small "small cards and wells at rest", but in-page surfaces are now
  flat by decision and no ui component uses a Surface material. Reconcile the
  docs page with the human. (The material-tooltip flag from tooltip's pass is
  resolved: chart's pass re-homed material-tooltip onto the chart tooltip
  bubble on 2026-08-16, though the "carries an arrow stem" copy is now stale —
  the chart tooltip has no arrow.) (Sidebar is no longer an open question: it inherits card's flat
  plain-border precedent; its own pass applies it in place.)

  the 8 hues, so the default palette's other colors (`sky-*`, `yellow-*`,
  `*-50`, `*-950`, …) still compile and get used by accident (badge-example's
  custom-color demos did until 2026-08-16; `bg-yellow-500` status dot in
  claimable-balance still does). Wipe the defaults with `--color-*: initial`
  in `@theme` so off-ramp colors fail loudly, or leave them available?

## Dependent notes (regressions filed against a not-yet-migrated component)

Filed by a migration pass that changed a contract its dependents relied on.
Each note is scope for the named component's own migration pass; delete the
note when that pass absorbs it.

- **input-group** (from input, 2026-08-16; textarea's pass confirmed the
  `InputGroupTextarea` variant live on 2026-08-16 — same mechanism, red-100
  fill with square-corner bleed on the invalid grouped textarea): the
  `InputGroupInput` / `InputGroupTextarea` reset list (`rounded-none border-0 bg-transparent …
  aria-invalid:ring-0`) predates input's migration and doesn't cancel the new
  invalid fill `aria-invalid:bg-red-100` — the compound variant out-specifies
  plain `bg-transparent`, so the inner control paints a *square* red-100
  rectangle inside the group's rounded border (visible corner bleed /
  "missing border" on invalid). Fix in input-group's pass: move the invalid
  fill to the group (`has-[[data-slot][aria-invalid=true]]:bg-red-100` on
  `InputGroup`, where it respects the rounding) and add
  `aria-invalid:bg-transparent` to the control reset. **combobox needs no
  separate fix** — `ComboboxInput` is `InputGroup` + `InputGroupInput` +
  a trailing addon button; it inherits both the bug and the fix.
- **kbd** (from tooltip, 2026-08-16): kbd styles itself inside tooltips via
  `in-data-[slot=tooltip-content]:bg-background/20`,
  `in-data-[slot=tooltip-content]:text-background`, and a dark-only dim
  `dark:in-data-[slot=tooltip-content]:bg-background/10`. Tooltip's pass kept
  the inverted contract pixel-identical, so these still render correctly
  (verified live, both themes) — but they are alias-spelled and the `dark:`
  `/10`-vs-`/20` split is a dark-only color override that decision 7 forbids;
  kbd's own pass must respell them in ramp vocabulary and stop-and-resolve
  whether the dark dim survives.
- **field** (from label, 2026-08-16): `FieldLabel` carried no weight of its
  own — it inherited label's `font-medium`, so field labels now render at the
  role's normal weight (400). That leaves `FieldTitle`, which still spells the
  old cluster raw (`text-sm font-medium`), visibly heavier (500) than
  `FieldLabel` — reconcile in field's pass. `FieldLabel`'s `leading-snug` was
  written against label's `leading-none` (it *loosened* 14px→19.25px); against
  `text-label-14` it now *tightens* 20px→19.25px (verified live: field labels
  compute 19.25px, so the dependent's line-height is unchanged pre/post).
  Field's pass should decide whether snug survives or the role's 20px leading
  takes over.
- **toggle-group** (from toggle, 2026-08-16): the group compensates for the
  outline shadow toggle no longer ships — `ToggleGroup` paints its own
  `data-[spacing=0]:data-[variant=outline]:shadow-xs` (now an off-system
  decision-2 violation to delete) and `ToggleGroupItem` carries the matching
  `group-data-[spacing=0]/toggle-group:shadow-none` reset (now dead). Item
  also spells `data-[state=on]:bg-muted` — alias-spelled and Radix-flavored
  (Base UI sets `aria-pressed`, not `data-state=on`, so it is likely dead);
  toggle's on-state is now `aria-pressed:bg-gray-alpha-300`, so delete or
  respell in toggle-group's pass and confirm flush groups still read. Toggle
  also gained button's press scale (`active:scale-[0.97]`, added 2026-08-16):
  in flush groups (`spacing=0`) a scaling segment opens gaps at the collapsed
  seams mid-press — toggle-group's pass must either suppress it there
  (`group-data-[spacing=0]/toggle-group:active:scale-100`) or accept the
  seam gap deliberately.
- **questionnaire** (from checkbox, 2026-08-17): not an import dependent, but
  `questionnaire.tsx` re-implements checkbox's box verbatim from stock
  (`rounded-[4px] border border-input dark:bg-input/30` + the
  `group-data-checked/…:*-primary` trio) for its choice indicator, so it now
  diverges visually from the migrated checkbox: dark-only wash vs the
  both-themes `bg-gray-alpha-400/30`, alias colors, literal radius.
  Questionnaire's own pass should import checkbox's calls (wash both themes,
  gray-1000 checked fill with background-100 tick,
  `rounded-[min(var(--radius-md),4px)]`; the radio variant keeps
  `rounded-full`).
- **sidebar** (from input, 2026-08-16): `SidebarInput`'s override
  `bg-background shadow-none` now cancels input's wash
  (`bg-gray-alpha-400/30`) via tailwind-merge, and the `shadow-none` is dead
  (migrated input ships no shadow). In sidebar's pass: decide whether the
  solid background is deliberate; migrate or delete the alias override.
